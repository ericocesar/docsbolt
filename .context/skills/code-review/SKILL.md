## Workflow

1. Get the diff and its shape: `git diff main...HEAD --stat`, then read the full diff for `apps/server/src/common/**`, `apps/client/src/lib/**`, `database/migrations/**`, and `integrations/outbound/**` first — those have the widest blast radius.
2. Classify each file as upstream-shared (core domain modules, `packages/editor-ext`, build config) or fork-local. Heavy rewrites of upstream files are a review comment in themselves.
3. Check placement and licensing: server code in `core/` vs `ee/`, client code in `features/` vs `ee/`. Grep the diff for imports crossing `ee/` in the wrong direction — `core` must never import `ee`, because `EeModule` is loaded by runtime `require` and a bad import only fails at boot.
4. Walk every new or changed Kysely query for a `workspaceId` predicate. Walk every new route for reachability after `DomainMiddleware`; any new entry in the allowlists in `main.ts` or `core.module.ts` needs an explicit justification.
5. Check the authorization chain separately from authentication: `JwtAuthGuard` authenticates, `SpaceAbilityFactory` / `PageAccessService` authorize, and a `Feature` key only gates availability — it is not a permission check.
6. Compare each DTO against the client payload. With `whitelist: true` in the global `ValidationPipe`, any undeclared field is silently stripped.
7. Verify pairing rules: `@SkipTransform()` on the server ↔ `exemptEndpoints` in `apps/client/src/lib/api-client.ts`; new env var ↔ `EnvironmentService` getter ↔ `.env.example` ↔ (if client-visible) the `define` allowlist in `apps/client/vite.config.ts`.
8. Review migrations as both schema and ordering: timestamp name sorted correctly against upstream, tenant columns present, indexes for the intended queries, rollback considered, and `db.d.ts` regenerated by `migration:codegen` rather than hand-edited.
9. Confirm page-content writes go through `collaboration.util.ts` / `yjs.util.ts`, and that outbound URLs built from user input go through `OutboundUrlGuard` / `OutboundAgentFactory`.
10. Check tests: a spec per new decision, a regression test per fix, `mock-providers.ts` updated for changed constructors. Then run the gate yourself for high-risk diffs and group findings as blocking / should-fix / optional.

A finding written the way it should be:

> **Blocking — cross-tenant read.** `apps/server/src/database/repos/label/label.repo.ts:42` — `findByPageId` filters by `pageId` only. A caller with a page id from another workspace gets that workspace's labels. Add `.where('labels.workspaceId', '=', workspaceId)` and thread `workspaceId` from `LabelService`, matching `page.repo.ts`.

## Quality Bar

- Findings are specific: file, line, the failure scenario, and the fix. "Consider improving error handling" is not a finding.
- The invariant list is checked explicitly, not assumed: tenant scoping, layered authorization, `core`↛`ee`, single content writer, envelope pairing, guarded egress, config via `EnvironmentService`, SQL only in repos.
- Documented exceptions are **not** flagged as bugs: unauthenticated `/share/*` and `/docs/*`, self-CSP on `/api/files/*`, tenancy bypass for `/api/billing/stripe/webhook` + `/api/auth/setup` + `/api/health*`, the `try/catch` EE require, and the `decorateReply` shims in `main.ts`.
- The linter's blind spots are covered manually: `no-explicit-any`, `no-unused-vars`, and `ban-ts-comment` are **off** in `apps/server/eslint.config.mjs`, so `any` creep, dead code, and `@ts-ignore` must be caught by eye.
- Formatting is not a finding — Prettier owns it. Note that `apps/server` uses single quotes (`.prettierrc`) while `apps/client` uses Prettier defaults; do not ask for one to match the other.
- "Tests pass" is never sufficient evidence for collaboration, uploads, exports, shares, or SSO — ask what was verified by hand, since CI runs no tests at all.
- New dependencies are questioned against the `overrides` / `minimumReleaseAge: 4320` policy in `pnpm-workspace.yaml`.
- Every blocking finding is actionable in this diff; anything larger is filed as follow-up rather than used to block.
