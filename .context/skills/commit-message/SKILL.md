## Workflow

1. Read the staged diff (`git diff --cached --stat` then the relevant hunks). Do not write a message from memory of what you intended.
2. Pick the type: `feat`, `fix`, `chore`, `docs`, `build`, `refactor`, `test`, `perf`, or `merge` (this repo uses `merge:` for upstream-sync commits).
3. Pick the scope from the paths touched — the scope is mandatory in this repo's history:
   - `apps/server/src/**` → `server` (or a narrower one already in use: `mcp`, `security`, `migrations`)
   - `apps/client/src/**` → `client`
   - `apps/server/src/database/migrations/**` → `migrations`
   - `Dockerfile`, `docker-compose.yml`, build config → `docker` or `build`
   - dependency/security bumps → `security`
   - `.context/**`, `docs/**` → `docs` (planning documents use `docs(sdd)`)
   - `packages/editor-ext/**` → `editor-ext`; `packages/base-formula/**` → `base-formula`
4. Write the subject in lowercase imperative, no trailing period, ideally ≤72 characters: `<type>(<scope>): <what changed>`.
5. Split the commit if the diff crosses concerns. This repo's history is many small vertical commits per feature (client type → component → DTO → service → repo), which keeps upstream merges tractable.
6. Add a body only when the *why* is not obvious: the root cause for a fix, the advisory ID for a security bump, the upstream conflict resolved for a merge.
7. For security fixes, cite the advisory (`GHSA-…`) in the subject or body.
8. Do not mention build artifacts, generated files, or `.env`. If `apps/server/src/database/types/db.d.ts` changed, say the migration caused it — that file is generated by `migration:codegen`.
9. Append the Co-Authored-By trailer if the change was AI-assisted and the user asked for attribution.
10. Verify: `git log --oneline -5` after committing, to confirm the message reads consistently with its neighbours.

## Examples

```
feat(server): inject subpages block on page creation when autoSubpages is enabled
```

```
fix(client): keep tree actions visible while menu is open
```

```
fix(security): update nodemailer to 9.1.1 to resolve GHSA-2x7j-588g-ccc2
```

```
fix(migrations): rename siem-destinations migration to follow fork execution order

Fork-only migration sorted before the upstream oauth migration, so a fresh
database applied siem_destinations against a schema that did not exist yet.
Renamed with a later timestamp; no data migration needed.
```

## Quality Bar

- Type and scope are both present; a bare `update stuff` or a scopeless `feat:` does not match this repository.
- The subject describes the change, not the file list. `feat(client): add AutoSubpagesToggle component` beats `feat(client): update space settings`.
- One concern per commit. If the subject needs "and", split it.
- `fix(...)` commits imply a regression test exists — if there is none, either add it or say why in the body.
- `feat(server)` touching the schema implies a migration plus regenerated `db.d.ts`; mention the migration if it is the point of the commit.
- Security bumps name the advisory; without it, the commit is unauditable later.
- `merge:` commits state what was reconciled, since the fork's merge history is read during the next upstream sync.
- Never commit `.env`, `.github/infra/portainer.*.env` with real values, `logs`, or anything under `docs/historico/` by hand — those are script-generated.
- Machine-generated `Build <timestamp> - sha-<short>` commits come from `scripts/build-and-push-ghcr.sh`; never hand-write or amend them.
- Imperative mood, lowercase after the colon, no trailing period.

## Resource Strategy

- No helper files are needed for this skill; everything required is the staged diff plus the conventions above.
- The authoritative reference for scopes is the repository history itself: `git log --oneline -40` shows the live convention better than any list.
- Commit-message rules belong here and in [development-workflow.md](../../docs/development-workflow.md#branching--releases); do not duplicate them into a third place.
- If the project ever adopts commitlint or a hook, this skill should point at that configuration instead of restating rules — check `.github/` and root config before assuming none exists.
- Escalate rather than guess when the scope is genuinely ambiguous (a change spanning `server` and `client` in one commit usually means the commit should be split).
