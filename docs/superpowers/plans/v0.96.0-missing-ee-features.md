# v0.96.0 EE-submodule features — fork gap audit

Generated by Task 4 of the v0.96.0 merge plan (`2026-09-08-v0.96.0-upstream-merge.md`).

**Decision (locked, controller ruling):** this merge keeps the fork's in-repo `apps/server/src/ee/` and drops the upstream gitlink. Features that v0.96.0 added **inside the upstream EE submodule** are NOT included in this merge; they need a follow-up porting plan. Features that v0.96.0 added **in the main tree** (either as new top-level modules like `apps/server/src/integrations/encryption/` or as new `apps/client/src/ee/<feature>/` directories) ARE auto-included in this merge.

> **Note on the previous version of this file:** the first draft misclassified several features as "missing in the EE submodule" when they are in fact main-tree files that the merge auto-adds. Specifically: encryption, outbound URL guard, SIEM client UI, SIEM destinations migration, and SIEM transactional emails all ship as regular files in `apps/server/src/integrations/` and `apps/client/src/ee/siem/`, not inside the `apps/server/src/ee` gitlink. The corrected gap analysis below reflects that.

## What the upstream EE submodule is

The merge's upstream gitlink recorded in the v0.96.0 tag points to commit `5e7120dcc86a344f5af09ccda0a29d5784659938`:

```text
160000 commit 5e7120dcc86a344f5af09ccda0a29d5784659938	apps/server/src/ee
```

with this `.gitmodules` entry in v0.96.0:

```ini
[submodule "apps/server/src/ee"]
	path = apps/server/src/ee
	url = https://github.com/docmost/ee
```

**The upstream EE repository is private.** `git clone https://github.com/docmost/ee` returns `Repository not found` (404) for the fork owner:

```text
Cloning into '/tmp/ee-upstream'...
remote: Repository not found.
fatal: repository 'https://github.com/docmost/ee/' not found
```

Therefore the **full working tree of the EE submodule cannot be enumerated locally**. The paths below were reconstructed from:

- the merge brief and Task 4 prompt (which listed upstream submodule features as `siem`, `ai`, `mcp`, `encryption`, `ee.module.ts`),
- the v0.96.0 main tree, which `require()`s `./ee/ee.module` and ships `apps/server/src/app.module.ts` with `EncryptionModule` and `OutboundModule` already imported from main-tree locations,
- and the upstream commit log between `v0.95.0..v0.96.0`.

This means the **follow-up scope listed at the bottom is partial**. Anything the EE submodule ships that did NOT have a matching main-tree file in v0.96.0 (or that was not explicitly named in the merge brief) is not enumerated here. A future plan should gain access to the private EE repo (or to an extracted tarball) before attempting the port.

## Where paths actually live

Three locations matter, and the table below distinguishes them precisely:

1. **`apps/server/src/ee/`** — the EE submodule gitlink. Contents are NOT in this merge; they live in the private `docmost/ee` repo at commit `5e7120dc`. The fork has its own in-repo `apps/server/src/ee/` (regular tree) which is preserved by this merge.
2. **`apps/server/src/integrations/`** and similar top-level `apps/server/src/...` paths — regular main-tree files. Anything new in v0.96.0 here auto-merges into the fork.
3. **`apps/client/src/ee/<feature>/`** — regular main-tree files on the client side (no submodule). Anything new in v0.96.0 here auto-merges into the fork.

The audit below lists v0.96.0 EE-tagged features by their **actual location**, not their conceptual home.

## Pre-existing fork decision (locked): restoring deleted files

Before this merge, the fork had **deleted** two v0.96.0 main-tree paths that the merge will **restore** because adopting v0.96.0 is now the goal:

1. **`apps/client/src/ee/siem/`** — all 9 SIEM client files (components, lib, queries, services, types) were absent from the fork's `main`. The merge auto-restores them.
2. **`apps/server/src/integrations/transactional/emails/siem-destination-{disabled,failing,recovered}-email.tsx`** — all 3 SIEM transactional email templates were absent from the fork's `main`. The merge auto-restores them.

This is **intentional**. The fork's earlier deletion of these files was the same "we don't need SIEM" choice that is now reversed by adopting v0.96.0. Task 4 authorizes the restoration.

(For reference, the deletion appears to predate the fork-specific EE work tracked in `apps/server/src/ee/`; the fork kept its own EE modules while stripping upstream's emerging SIEM client and email code. This merge reverses that on the auto-merge paths only; the fork's EE modules in `apps/server/src/ee/` are not touched.)

## Follow-up scope (partial — see caveat)

Given the EE submodule's private status, the follow-up scope is the union of:

1. **Confirmed missing (table rows marked "yes — port"):**
   - SIEM backend (`apps/server/src/ee/siem/`) — destination model, ingest endpoints, queue workers, streaming.
   - Upstream v0.96.0 AI controls (after parity check against fork's `apps/server/src/ee/ai/` and `apps/server/src/ee/ai-chat/`).
   - MCP server backend (`apps/server/src/ee/mcp/`) — client UI already merged; server-side MCP transport is in the submodule.

2. **Verify-first (table rows marked "unknown"):**
   - Whether `apps/server/src/ee/encryption/` ships anything beyond what `apps/server/src/integrations/encryption/` already provides.
   - The submodule's `apps/server/src/ee/ee.module.ts` vs the fork's — decide canonical wiring.

3. **Enumerate-first (table row marked "unknown — submodule contents not fully enumerable"):**
   - Any submodule directory not surfaced by the brief or by main-tree hints. Follow-up requires repo access.

The follow-up plan should:

- clone or otherwise obtain `docmost/ee@5e7120dc` (request access from the upstream maintainers, or accept an extracted tarball);
- diff each submodule directory against the fork's in-repo `apps/server/src/ee/` and against any main-tree equivalents;
- produce a porting checklist with one row per file: "copy verbatim", "merge with fork's implementation", or "skip — already superseded by main-tree module";
- sequence the porting into the fork's in-repo EE tree, preserving the fork's existing modules;
- update the fork's `apps/server/src/ee/ee.module.ts` to wire the new ports without breaking existing modules.
