# docmost v0.96.0 Upstream Merge — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring the docsbolt fork up to upstream `docmost/docmost` v0.96.0 while preserving every fork-specific change (in-repo EE features, Portainer infrastructure, `boltplan` rename) unless the user explicitly authorizes the upstream replacement.

**Architecture:** A clean `git merge` of the `v0.96.0` annotated tag into a dedicated `merge/v0.96.0` branch, followed by systematic resolution of the 5 actual conflicts (3 UU + 1 UD + 1 DU) and a verification sweep of the 116 auto-merged files. The plan was originally written assuming 68 conflicts (based on `git merge-tree` prediction), but `git merge` itself only conflicts on **overlapping region** differences — most "modified on both sides" files auto-resolved. The structural surprise is that upstream ships `apps/server/src/ee` as a **gitlink/submodule**, while the fork has it as an **in-repo directory tree** of fork-specific EE code. Resolution: drop the upstream gitlink, keep the fork's in-repo EE. No `git rebase` — we want a true merge commit so the divergence history stays auditable.

**Tech Stack:** Git, pnpm 11.x, Node 26, NestJS 11 (server), React 19 + Mantine 9 (client), Kysely, portainer-stack deploy via `scripts/deployportainer.sh`.

**Spec:** This plan IS the spec for the v0.96.0 merge. There is no upstream design doc to argue from — the plan enumerates every change between `v0.95.0..v0.96.0` and dictates resolution per file.

- **Default resolution = keep local (fork).** Adopt upstream only when explicitly justified in the task ("Important" tag, requires user authorization).
- **No force pushes, no `git reset --hard`, no rewriting published history.**
- **Work happens on `merge/v0.96.0` branch in a dedicated git worktree** (`../docsbolt-merge-v096`). `main` is not touched until verification passes.
- **The merge is currently in dirty state** (post `git merge --no-ff --no-edit v0.96.0`) — 5 unmerged paths, 192 files modified/added/deleted in working tree. **Do not `git merge --abort`** — aborting would discard 192 files of pre-merge work already in the working tree.

- **Commit after every task**, conventional commits with scope (`merge`, `deps`, `ee`, `infra`, `fix`).

**Critical structural decision (load-bearing):** v0.96.0 ships `apps/server/src/ee` as a **gitlink/submodule** (mode 160000) pointing to `https://github.com/docmost/ee@5e7120dc`. The fork's `apps/server/src/ee/` is a **regular directory tree** (mode 040000) of in-repo EE code (`api-key/`, `scim/`, `sso/`, `mfa/`, `page-verification/`, `ai-chat/`, `ai/`, `audit/`, `base/`, `template/`, `security/`, `ee.module.ts`) inlined by the fork's commit `08d14516 chore(ee): replace ee submodule with in-repo implementation`. **Resolution: drop the upstream submodule gitlink, keep the fork's in-repo EE tree.** This means v0.96.0 features that live inside the upstream EE submodule (SIEM backend, AI controls, MCP OAuth, MCP server, encryption, transactional email SIEM templates, etc.) do **not** land in the fork by this merge alone. Those features need to be cherry-picked or ported into the fork's in-repo `apps/server/src/ee/` in a follow-up plan. Task 4 of this plan audits which v0.96.0 features are missing and flags them for the user.
